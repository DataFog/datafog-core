Core follows semantic versioning across Rust, Python, Node.js and browser WASM.

| Release | What can change |
| --- | --- |
| Major | Incompatible changes to a published API, error code, range unit, transformation design or protocol version. |
| Minor | Detectors, supported platforms, optional engines and APIs. Fixes that change findings or spans ship in a minor release, as do corrective privacy fixes such as tightening mask reveal limits. |
| Patch | Fixes that preserve findings, spans and error codes for previously working inputs. |

When upgrading across minor versions, check the affected entities and rerun representative inputs. For example, [Core 1.8.0](/releases/1-8-0) changes EMAIL spans where addresses touch text in another script.

## Range and support contracts

All ranges are zero-based and end-exclusive. Byte offsets count UTF-8 bytes, code-point offsets count Unicode code points, and JavaScript UTF-16 offsets count code units. A structured finding's offsets refer to the decoded string at its JSON Pointer path.

The two latest minor releases of the current major receive fixes. Older minor releases receive security fixes only. Experimental surfaces can change in a minor release. See the [versioning policy](https://github.com/DataFog/datafog-core/blob/main/VERSIONING.md) for deprecation windows and experimental APIs.

## Capability contract version

The capability response carries `contract_version: 1`. This version identifies
the meaning and structure of the capability contract, independently of the
package version. Compatible additions such as an additional entity, locale, or
optional metadata field retain contract version 1. Changes to existing capability
field meanings or incompatible structure require a contract-version increment.

See the [capabilities reference](/reference/capabilities) for the generated
inventory and activation metadata.
